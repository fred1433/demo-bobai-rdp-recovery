An interrupted save, recovered without a second submission.

A small attended executor completes one prepared transaction in an application it sees only as the pixels of a remote desktop window. In this run it is killed right after clicking Save. When it starts again it does not know whether the save went through, so it searches, reopens the record and compares every value before doing anything else.

After an interruption, it verifies the result before any new submission. If it cannot conclude, it stops.

Case DEMO-HH-014, period 2026-11

Recorded test. FreeRDP client on macOS, Linux xrdp host. Synthetic application and data. Windows client not tested. Real time, no sound; the first 8 seconds repeat the restart moment.

When the screen proves nothing, it stops

Here the application accepts the Save but returns to its list without a confirmation, and the list lags behind. The executor searches 3 times over 17 seconds and finds nothing.

An empty list does not prove that nothing was saved, so it stops with assistance required and does not submit again.

The check on the host afterwards: 1 record for DEMO-HH-014, 2026-11. It had been saved. A second submission would have made a duplicate. Save clicks in the journal: 1.

What actually ran

The bench

Workstation sidemacOS 27.2 on Apple M1 Max. FreeRDP 3.32.2 client, drawing into a virtual screen (Xvfb in a container, localhost only) so the real desktop is never captured or typed into.
Remote sideDebian 12 container with xrdp 0.9.21.1. It runs the synthetic application and nothing from the executor.
ApplicationSynthetic, written for this test: search, two-tab form, Save, saved-record list, read-only record. It accepts duplicate saves on purpose.
Reading the screenTesseract 5.5.2, local. Each value is read by four OCR variants that must agree three times out of four, else it counts as unreadable.
ModelQwen2.5-VL 7B Instruct (Apache-2.0) through Ollama on the same Mac, only when the screen matches no known state. It returns a label from a fixed list and never clicks.
Remote model APINone. Cost 0 $.

The code, and what a first call would cover

The repository is meant to be read by the engineers who already own your desktop workflows. The parts that matter:

  • executor/run.py: the one place where Save may be clicked, and the recovery path where it may not.
  • executor/journal.py: the submit intent is written and flushed to disk before the click.
  • executor/screen.py: capture of the client window and local input. It is the only file a Windows port replaces.
  • executor/ocr.py and executor/vision.py: reading values from pixels; the model is called only on an unknown screen and returns a label from a fixed list.
  • scripts/scenario.py: replays every case above, with the operator and the faults played by a separate process.

Not covered here: your application, your platform and data, your remote desktop client, a Windows workstation (capture and input permissions, display scaling), scrolling and longer transactions.

Fifteen minutes with you or the engineer who owns the automation: which remote desktop client your customers use, a walkthrough of the transaction, and how the application shows a saved record. That is enough to say what of this carries over.
